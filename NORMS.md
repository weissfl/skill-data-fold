# NORMS — реестр норм data-fold (RU, каноническая версия на момент фиксации)

Назначение: приёмочный чек-лист безпотерьности для EN-адаптации со сжатием.
Правило: каждая строка должна иметь носителя в EN-версии; норма без носителя = потеря.
Нумерация сквозная; группировка по разделам SKILL.md.

## Goal
1. Идеальное состояние: каждое утверждение в выводах проверено или явно помечено непроверенным с указанием, кто и как закроет.
2. Сходимость: реестр открытых вопросов пустеет; противоречия сняты или зарегистрированы с владельцем.
3. Итог: упакованный срез проверенных данных, достаточный для заявленного действия без возврата к сырым источникам.
4. Действие — якорь достаточности: заявляется человеком, уточняемо по ходу; без заявленного действия цель неопределима.

## Task — контракт шагов
5. Приём: порция любой формы → единицы — минимальные утверждения, подтверждаемые/опровергаемые независимо.
6. Приём: цифровые артефакты сохраняются в директорию задачи.
7. Статусирование: происхождение (источник, время, канал; выводу — опоры) и статус, меняемый только операциями.
8. Развилка: влияющей на решения единице — одна ветвь: проверить самому / спросить источник / дефолт с меткой чьё решение.
9. Дельта спроса: реестр пересчитывается — закрылось, осталось, родилось.
10. Упаковка: без блокирующих вопросов продукт из проверенных единиц; спорное, дефолты, открытое — отдельными разделами.
11. Определение: блокирующий = открытый вопрос, без которого заявленное действие не строится.
12. Список шагов — состав, не порядок; порядок исполняет машина состояний.

## Task — Вход
13. Цикл запускает дельта: сведения без статуса, вопрос без ответа, противоречие.
14. Сообщение человека любой полноты; цель и критерий достаточности заданы навыком, не входом.
15. Симметрия: любой участник запускает любой шаг; требование человека = вход состояния.

## Task — Действие
16. Действие заявляет человек при входе; задаёт стартовый состав реестра спроса.
17. Реестр разворачивается из действия вопросом «что нужно знать, чтобы действовать?».
18. Незаявленное действие — первый блокирующий вопрос реестра.
19. Уточнение: человек сам или подтверждает предложение исполнителя; замена ребром «заменяет» в том же векторе; реестр переразворачивается; проверенные данные наследуются.
20. Действие всегда одно; составное декомпозируется — замена по вектору или новая задача со своей директорией.

## Task — Состояние
21. Граф единиц, связей, операций и спроса; форма — state_shape.
22. Живёт в пределах задачи; после неё значим только продукт.
23. При малом спросе граф живёт в диалоге; материализация при росте связей или переходе задачи через сессию.
24. Материализация переносит граф целиком: реальность одна, файл — запись.
25. Импорт данных прошлых задач — только обычным приёмом, как новые единицы.

## Environment
26. Источники по доступу: владеют целью / знают среду / доступны без диалога (чтение или выполнение); у каждого свой язык.
27. Маршрутизация по доступу: вопрос о цели — владеющему целью, о среде — знающему среду.
28. Каналы множественные и теряющие; сведения приходят не тем маршрутом и не в один момент.
29. Источники отвечают с задержкой, не по существу или молчанием; молчание — тоже данные.
30. Среда меняется без ведома конвейера: любая проверка — снимок момента.
31. Исполнитель дрейфует без внешних опор: интерпретация за факт, потеря пометок; опоры — в состоянии, не в памяти.
32. Экономика: круг общения с источником дорог; проверка инструментом обычно дешевле.

## Машина состояний — общие правила
33. Состояние держится до выполненного GOAL; между репликами — возврат к текущему состоянию по триггеру.
34. Активны несколько состояний — исполнение в порядке цикла, каждое до своего GOAL.
35. Переход вперёд без выполненного GOAL предыдущего — ошибка.

## Состояния
36. intake: триггер — пришла порция сведений.
37. intake: разбить на единицы, назначить происхождение (выводу — опоры).
38. intake: дедуп по тезису — повторная доставка любым каналом не разворачивается, дописывается происхождением; сама по себе независимым подтверждением не считается, независимость — только по протоколу 4.
39. intake: GOAL — нет единиц без происхождения; остаток порции держится до полной обработки.
40. status_fork: триггер — единицы с происхождением без ветви.
41. status_fork: назначить TYPE из таксономии кейса; влияющим — ветвь.
42. status_fork: GOAL — влияющие с ветвью; без ветви — явно отложены с причиной.
43. verify: триггер — выбранная ветвь не исполнена.
44. verify: исполнить выбранную ветвь — проверка инструментом / вопрос источнику / фиксация дефолта с меткой владельца.
45. verify: до ответа ветвь открыта — вопрос держит её в реестре; исполнение длится репликами и сессиями.
46. verify: молчание — данные: повторный вопрос без ответа → дефолт с владельцем-человеком либо датированный вопрос; блокирующее молчание → freeze.
47. verify: GOAL — каждая единица: подтверждение (ребро «подтверждает») / зарегистрированный вопрос / маркированный дефолт.
48. demand_delta: триггер — закрылся вопрос или поглощена порция.
49. demand_delta: пересчитать реестр; новым вопросам — ветвь и владелец закрытия.
50. demand_delta: GOAL — реестр соответствует картине; ни один новый вопрос вне реестра.
51. package: триггер — нет блокирующих вопросов.
52. package: продукт из проверенных; единицы «в моменте» — с пре-чеком на момент сборки; спорное/дефолты/открытое — в явные разделы; сирота-аудит; передача человеку.
53. package: GOAL — человек утвердил; до утверждения состояние держится; правки человека — новые единицы через цикл.
54. freeze: триггер — блокировка извне (источник недоступен, исполняет свою часть или разрешение противоречия заблокировано) и ни один шаг не продвигает картину.
55. freeze: зафиксировать открытые вопросы, блокировщиков, условия снятия; тупиковый отчёт; остановить цикл.
56. freeze: GOAL — отчёт передан человеку; задача заморожена с явным условием возобновления.

## Протоколы
57. П1 Происхождение обязательно: источник, время, канал; выводу — опоры; без происхождения — не в выводах и не в продукте.
58. П1 Разрешимость ссылки: сеть — URL первоисточника (+ артефакт-снапшот парой); файл — путь относительно data-folds/; реплика — канал, лицо, дата; проверка — инструмент и дата, воспроизводимо; имя без места запрещено.
59. П2 Производное — не факт: вывод без независимого подтверждения не получает «проверено».
60. П3 Слова исполнителя — единицы: произнесённые и внутренние выводы входят приёмом; миновать приём запрещено; доверие не подразумевается, влияющее проверяется как чужое.
61. П4 Подтверждение тянется к первоисточнику: первоисточник = прямой доступ к факту (например: норма/инструмент/заявляющий); пересказ вторичен; подтверждение не ниже требуемой глубины; одно происхождение — не независимость; глубина растёт с ценой ошибки; недостигнутая глубина при высокой цене — вопрос в реестр.
62. П5 Срок годности: известен — дата/диапазон, живой дедлайн — вопрос с датой; неизвестен — VALIDITY="в моменте", пре-чек при опоре; условие — метка условия, пре-чек при опоре или сигнале; устаревшее замещается (датированная история, не ложь и не удаление); вывод наследует кратчайший срок опор.
63. П6 Понижение по цене ошибки: поданное как факт без подтверждения при цене ошибки выше цены паузы — не основание выводов и действий и не утверждается фактом ни в одном исходящем сообщении; держится сигналом, запускается верификация.
64. П7 Дельта спроса после каждого приёма и каждого закрытия вопроса.
65. П8 Закрытие с вердиктом соответствия: записываются форма вопроса и субстанция ответа; ответ «не о том» не закрывает; зависимый вопрос (ребро «зависит-от») не закрывается при открытой опоре.
66. П9 Дефолт маркирован: чьё решение — человека или исполнителя; в продукте разделом на подтверждение; по осям владельца цели дефолт запрещён — только вопрос; молчание = принятие только при явном объявлении.
67. П10 История меняется только свёрткой: сжатие — узел-сводка с ребром «заменяет»; оригиналы не выбрасываются в обход операций; файл состояния правит только цикл.
68. П11 Противоречие регистрируется: ребро «противоречит» + пункт реестра с владельцем снятия; обе стороны сохраняются; снятие — заменой или опровержением стороны; молчаливый выбор стороны запрещён.
69. П12 Продукт только из проверенного: спорное, непроверенное, открытое — в явные разделы, не в тело.
70. П13 Сирота-аудит перед упаковкой: единица без происхождения, вопрос без ответа, вывод без опор — обнаружены и обработаны (закрыть/проверить/оставить открытым).

## Гайды
71. Таксономия под кейс: 1–2 слова по логике домена; не наследуется, не строится заранее; ядро одно для любых доменов.
72. Приоритизируй потоки: сначала то, что разблокирует других или несёт больше зависимостей.
73. Не спрашивай о проверяемом: достижимо инструментом — провери, спрашивай с фактом; вопрос за один круг.
74. Дозревай вопрос: первое «не по существу» — готовь бинарную форму с фактом и осями важности; второе — отправляй.
75. Не предлагай неподтверждённое: вариант без подтверждённой осуществимости человеку не предлагается.
76. Дозируй источник: объединяй вопросы; язык и тон получателя; не обещай следующий этап при незакрытых вопросах участников.

## state_shape
77. Узел: тег snake_case по сути; TYPE 1–2 слова таксономии; аннотация 1–2 предложения (происхождение-разрешимое по П1, время, канал).
78. Узел: у проверенных — PRIMACY="первичная|вторичная" (глубина градуированной лестницы — в аннотации, PRIMACY — бинарная граница) и VALIDITY (дата/диапазон · условие · «в моменте»).
79. Узел: происхождений может быть несколько — повторные доставки.
80. Операции: журнал над узлами; статус = свёртка операций; записи — только добавление и замена.
81. Статусы: непроверено · проверено · опровергнуто · замещено.
82. Рёбра: заменяет · противоречит · выведено-из · подтверждает · зависит-от.
83. Реестр спроса: открытые вопросы с ветвью, владельцем закрытия, датой для дедлайнов и вердикт-записями закрытия (форма вопроса — субстанция ответа).
84. Артефакты: любые цифровые доказательства с любой стороны; имя art-<номер>-<подсказка>.<расширение>; ссылка атрибутом ARTIFACT.
85. Хранение: data-folds/ в корне воркспейса; задача — data-fold-<слаг>/ с черновиком data-draft-<слаг>.xml, продуктом data-fold-<слаг>.xml и артефактами; черновик в пределах задачи; перенос задачи = перенос директории.

## product_shape
86. Скелет инвариантен: корень с ACTION, TASK, CREATED; разделы verified / defaults / open.
87. verified: единицы с тегами, TYPE, происхождением, статусами, рёбрами, первичностью и сроком годности.
88. defaults: дефолты с меткой чьё решение.
89. open: вопросы и зарегистрированные противоречия с владельцем, условием снятия блока, датой дедлайна.
90. Подача verified адаптивна под действие; скелет разделов неизменен.
91. Имя data-fold-<слаг>.xml; валидный XML; в директории задачи.
92. После задачи самостоятельная ценность — только у продукта; артефакты остаются приложениями.
93. Пример-прайминг: ORIGIN+ARTIFACT пара, PRIMACY двух вкусов, VALIDITY («в моменте» и условие), BRANCH/OWNER/UNBLOCK у открытого вопроса, CREATED у корня.

## tactical_freedom
94. Локальные решения за исполнителем; перечень не исчерпан (глубина/порядок проверок, форма вопросов, момент материализации, диалог, число попыток).
95. Границы: протоколы обязательны, гайды эвристичны.

## completion_criteria
96. Success: нет блокирующих; противоречия разрешены или зарегистрированы с владельцем; сирота-аудит чист; продукт из проверенных с явными разделами; человек утвердил.
97. Rollback: отвержение упаковки — правки человека как новые единицы, пересборка.
98. Fail-safe: блокировка извне (источник недоступен, исполняет, разрешение противоречия заблокировано) — заморозка с тупиковым отчётом (что открыто, кем заблокировано, что снимет); легитимный выход, не провал.
99. Zero-context survival: продукт несёт полную мета-разметку — теги, происхождение, статусы, первичность, сроки годности, дату сборки.

## Глобальные
100. Frontmatter: name=data-fold; description = триггер (уникальный глагол + продукт + домен).
101. Блоки PCAM: goal/task/environment/working_patterns/tactical_freedom/completion_criteria, fencing парными тегами.
102. Out-of-scope (зафиксировано решением): аудитория продукта и now/will-дельта — жанр следующей стадии, не data-fold.
